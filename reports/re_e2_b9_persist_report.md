## 3. 方向 B（外部 watch 优化）上限分析

### 3.1 捕捉窗口（✅ 字节级 + 实机日志）

- 有效写窗口 W = **[pending 构造, 状态1 分叉评估]**——b9 必须在 0x6045c4 之前落地。分叉后（返回 1）→ 状态 6 → 5→7→8→9→10，**单 tick 可走完**（40 §3.1）。
- 构造器写状态 9（§2.1 尾部 `push 9`），之后状态机走到状态 1 分叉；**watch 实测**：部分 pending 在 state=1 停留 >50ms（被捕获），多数在 50ms 内完成 1→6→…→10（仅见 state=10）。
- **★state=9 是双义状态**（构造初值 与 结算尾部 同值）：watch 在 state=9 抓到 0x4afea020 写入 b9 仍走 10（word54=1 = 分叉早已返回 1）→ **state<10 条件会假捕获**（写无效）。

### 3.2 实测捕捉率（✅ `_elev__re_b9_forge.log` 08-19 会话）

- 该会话 6 场新 pending：1 场 state=1 捕获 → 写 → 状态4 加载 ✅（0x35af8ff8）；1 场 state=9 假捕获（0x4afea020，写无效）；4 场只见 state=10（0x2dd9f000/0x2dd9e698/0x2415a938/0x2dd6e348，完全漏）。
- **有效捕捉率 ≈ 1/6 ≈ 17%，漏 ≈ 83%**——量化了用户「很多战斗没捕捉到」。

### 3.3 理论上限

- 捕捉率 ≈ P(采样落在 W) ≈ W/T（W<T 时）。W 分布未知但经验常 <50ms；T 受 Python+ReadProcessMemory 开销限制：
  - 50ms（现状）：~17%（实测）。
  - 5ms：W>5ms 的场次 ~全中；W<5ms 仍漏。
  - 2ms：Python ctypes RPM 多字段读取 + 调度抖动，2ms 可行但边缘；W<2ms（同 tick 构造+分叉，tick 可快于 2ms）**结构性不可捕捉**。
- **结论：轮询再快也到不了 100%**——只要构造与分叉发生在同一 tick（或 tick 快于轮询周期），外部进程永远来不及写。唯一 100% 路径 = 引擎内写（分叉/构造时同步执行）。

### 3.4 方向 B 备选：HWBP 挂钩构造器（评估为不推荐）

- 提案：DebugActiveProcess + 硬件断点（DRx）挂 0x57191a/0x571f30/0x572647（b9 写点，构造时必执行）。
- 评估：①`re_h47_hwbp.py` 历史：DebugActiveProcess 附加后 breakpoint 事件流异常卡游戏（已记录）；②每次构造都触发调试器往返（~0.5-2ms 停游戏），构造频率在 CAI 处理期可达每秒多次；③须在陷阱中改 al 寄存器再单步（复杂）；④DR 寄存器仅 4 个，3 个写点可用。
- **判定：技术上可达 100%，但路径历史不良 + 复杂度高，严格劣于方向 A1（进程内 hook 基建成熟）。**

## 4. 方向 A（引擎内嵌常驻）候选挂点静态分析

### 4.1 ★A1：FUN_105caa60 入口 hook（0x5caa60）——推荐主选

**原理**：入口 5 字节 JMP（原字节 `53 56 8B F1 57` = push ebx/push esi/mov esi,ecx/push edi，✅ 干净 JMP 点）→ stub：过滤 → 写 [ecx+0xb9]=1 → 重放原 5 字节 → jmp 回 0x5caa65。函数体随后读到 b9=1 → 返回 0 → 状态 4。**分叉必执行 → 捕捉率 100%，零竞态**。

**过滤条件（stub 内，全部读 pending 对象，守卫式）**：
| 条件 | 字段 | 作用 |
|---|---|---|
| vt 匹配 | [ecx] == base+0x15fa8a4 | 确认为 pending（安装时注入实际 VA） |
| ready==0 | [ecx+0x55]==0 | AI 未登记（人类战斗 ready=1 → 不干预） |
| 非海战 | [ecx+0x58] ∉ [11,14] | S15 E1 类型筛选（btype 15=UNSPECIFIED 默认加载，宁多勿漏） |
| 单人局 | [[ecx+0x30]+8]+0x155c==0 | 排除双人类模式（0x155c 保护，守卫 2 级解引用） |
| 可选防劫持 | [ecx+0xf0]==0 | ⚠️ f0=「攻击源人类」标志（状态机 0x604307 分支）；防 FOTS 拒绝场景被劫持（见 §6）——实机定案后决定是否启用 |

**调用面影响（4 调用点逐一点评）**：
- 0x6045c4（决策）：★目标路径，返回 0 → 状态 4（预期）。
- 0x60459f（通知）：返回 0 → core+0x154 通知值 1→0。**语义 = 与人类加载一致**（人类分叉返回 0 也通知 0）🔶；且比外部写更一致（外部写可能让两次调用一 1 一 0，入口 hook 让两次都 0）。core+0x154+8 具体消费方未静态解析（运行时装配），🔶 中低风险。
- 0x604931（状态6 结算）：b9 生效后 pending 走状态 4，**永不达状态 6** → 不触发。若 hook 安装时 pending 已在状态 6（hook 晚装），0x604931 返回 0 → core+0x168 通知 0 → 仍写状态 5（流程不变，仅通知值变）——🔶 低风险。
- 0x5d94b4（管理器包装，战斗结束）：返回 0（b9=1 持久）→ core+0x168 通知 0。**与 08-19 外部写实机完全同态**（外部写 b9=1 后战斗结束正常回战役，用户确认链条完整）→ ✅ 已验证。
- **★整体风险 = 外部 b9 直写的已验证语义 + hook 机制自身风险**；b9=1 的后续行为（状态4→env→battle_mgr→旁观→战斗结束）已被 08-19 实机完整验证。

**注入方式**：inline JMP + VirtualAllocEx stub（re_h47_s5_hook/re_f10_host_observer 既有基建，capstone 自校验）。风险：中低（0x6045cc 同区 hook 已实机长期运行；0x5caa60 入口新点 ⚠️ 需 1 轮实机确认无代码校验拦截——游戏校验为「特定区域」（03 三十四节），0x604xxx/0x5caxxx 区无已知校验）。

**推荐度：★★★★★（首选）**。单点、100% 捕捉、语义已验证、可热卸（restore）。

### 4.2 A2：0x6045c4 调用点 hook（窄影响面版）

**原理**：hook 0x6045c4（E8 5 字节）→ stub：过滤 → 写 [ecx+0xb9]=1 → call 0x5caa60 → jmp 0x6045c9。只影响状态1 决策路径。
**影响面**：0x60459f（同一 tick 的首次调用）在 hook 前已返回 1（b9 未写）→ **通知 1 决策 0 不一致**——外部写同样存在（甚至更糟），实机未见副作用 🔶；但 A1 无此不一致（两调用都 0），A2 略逊。
**复杂度**：与 A1 相近（stub 同样要做过滤+写 b9），还多一次原函数重入。**推荐度：★★★☆☆（A1 的次选）**。

### 4.3 A3：构造器字节 patch 强制 b9=1（零 stub 备选）

**原理**：3 个构造器把条件随机写改为恒写 1。最小 patch（每点 ~7 字节，以 FUN_10571520 为例）：
- `0x5718f5 75 29`（jne ready!=0 跳过）→ `90 90`；`0x571901 76 1D`（jbe N<=0 跳过）→ `90 90`；
- `0x57190c E8 ...`（call RNG）→ `33 C0 90 90 90`（xor eax,eax; nop ×3，5 字节同长）→ random=0 ≤ N → setbe=1。
- 或 `0x571917 0F 96 C0`（setbe al）→ `B0 01 90`（mov al,1; nop，3 字节同长）。3 个构造器 × 各 2-3 处 = **9 处字节 patch**。
**影响面**：所有 ready==0 的 pending（AI 内战 + 潜在 FOTS 拒绝场景）都强制加载；**无 btype 海战过滤**（FUN_10571950 的 b9 写发生在 btype 写 0x5719f7 之后，可加读 [esi+0x58] 过滤——但 patch 复杂度上升）；无 155c 双人类防护（构造器不读 155c）。**推荐度：★★☆☆☆（简单但无过滤、影响面宽、补丁分散；仅当 A1 被实机否决时考虑）**。

### 4.4 ★A0：数据常驻（零代码——写 N 阈值让原生机制接管）

**原理**：原生写 `b9 = (RNG%101 <= N)`，N = `[[[attacker+0x160]+0x30]+0x20]`。若把 N 写 101（或 0x7fffffff），则所有后续 ready==0 的 pending 构造时原生 b9=1 → **引擎自驱加载，外部零轮询零竞态**。
**前置（⚠️ 需 1 轮实机）**：①定位 B = [[attacker+0x160]+0x30] 的对象同一性（per-faction？全局？——决定写几个对象）；②[N+0x20] 的其他读者（改 N 的副作用面）；③FUN_10571950 的 0x6a0cb0 分支（若为海战判定，N2=[B+0x24] 可能是海战阈值——**写 [B+0x20]=101 + [B+0x24]=0 可原生实现「陆战全加载 + 海战全跳过」**，🔶 推测待实机）；④FOTS 拒绝场景同 A3 风险。

## 5. 决策建议

### 5.1 推荐：方向 A1（FUN_105caa60 入口 hook），方向 B 降级为辅助

- **捕捉率**：A1/A2/A3/A0 全部 100%（写发生在分叉前/构造时，无竞态）；B 结构性 <100%（实测 17%@50ms，5ms 也到不了 100%）。
- **风险**：A1 影响面 = b9=1 语义，**已被外部直写实机完整验证**（08-19：状态4→env→battle_mgr→旁观→战斗结束回战役，零外交副作用）；A3 无过滤影响面宽；A0 对象语义未定案；B2 调试器路径历史不良。
- **维护**：A1 单点、可热卸、过滤逻辑可扩展（后续加规模粗筛只需改 stub）；A3 分散 9 点；B 无维护负担但无捕捉保证。

### 5.2 最小实现路径（A1）

1. **实机探测轮（1 轮，只读 + 观测 hook）**：
   - hook 0x5caa60 入口纯观测版（不写 b9，记录 4 调用点归属 + 输入集 ready/btype/count/[155c]/[f0] + N=[[[pending+0x30]+0x30]+0x20] 现值）；
   - 确认 vanilla AI 内战：f0==0 ✓、N==0 ✓（预期，与 §2.3 一致）、btype 分布；
   - **顺带 A0 探测**：读 [B+0x20]/[B+0x24] 现值 + 找 [B+0x20] 其他读者（xref 扫描）→ 判断 A0 是否可行。
2. **构建 A1 stub**：过滤（vt + ready==0 + btype∉[11,14] + 155c==0 [+ f0==0 实机定案后启用]）→ `mov byte [ecx+0xb9], 1` → 重放原 5 字节 → 返回。capstone 自校验（判定逻辑/指令边界/NULL 守卫）。
3. **注入集成**：`_run_elev.py` 加 `--b9-persist` 模式（启动游戏后装一次，会话内常驻；重开游戏重装——每次启动一条命令，即「常驻」）。

### 5.3 筛选职责分工（回答任务书「判定内嵌在哪层」）

- **引擎内（A1 stub）**：vt + ready==0 + btype（11-14 海战跳过）+ 155c==0（单人局）——这些是**确定性、零歧义、字节级便宜**的判据，必须内嵌（否则无法在分叉前过滤）。
