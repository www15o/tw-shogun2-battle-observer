## 0. 一句话机制

**两处必须同时写，缺一不可：**

| # | 写入目标 | 值 | 含义 |
|---|---|---|---|
| 1 | `faction + 0x6a0` | `0` | `FactionIsHuman` = 非人类 |
| 2 | manager 表中该派系条目 | `0` | `manager_id = FULL_MANAGER` |

**恢复人控** = 反向写回：`+0x6a0 = 1` + `manager_id = 7 (HUMAN)` —— **合法，且可正常存档**。
两者是同一套状态的两半：只写 manager 表（或只翻 `+0x6a0`）都**不成立**，见 §6。

## 1. 关键偏移与结构

### 1.1 faction 对象

| 偏移 | 类型 | 含义 | 证据等级 |
|---|---|---|---|
| vtable | — | `0x7a0bac30`（RVA `0x15fac30`） | 已确证 |
| `+0x4fc` | int | 国库 | 已确证 |
| `+0x6a0` | byte | `FactionIsHuman`（1=人类 / 0=AI） | 已确证 |
| `+0x6d8` | — | 状态集：人类**完整** / AI **空壳** | 已确证 |
| `+0x7a8` | byte | 已移交标志（`grant_faction_handover` 写此处） | 已确证 |
| `+0x0b14` | ptr | 派系中文名指针（UTF-16） | 已确证 |
| `+0x8c` | ptr | `→ [+8]` = campaign model（cm） | 已确证 |

faction 对象在内存中按数组排布，**间隔 `0xB88`**。

### 1.2 manager 表（挂在 obj_A 上）

| 偏移 | 含义 |
|---|---|
| `+0x644` | cap（**动态增长**——旧判据 `cap ∈ [40,100]` 会漏掉真对象，勿再用） |
| `+0x648` | cnt（条目数） |
| `+0x64c` | tbl（条目数组基址） |

条目结构 = `{key_obj_ptr, manager_id}`，其中：
- **key 直接就是 faction 对象指针**（当前主用路径）；或
- `key + 0x164 → faction`（S2 旧模式 / mode2，保留作回退兼容）

实测 **49 条全映射**。

### 1.3 campaign model 链

```
faction + 0x8c  →  [+8]  = campaign model (cm)
[cm + 0x14b0]   =  obj_A（campaign AI manager 表持有者）
[cm + 0x1498]   =  faction 数组容器（+0x40 = cnt / +0x44 = base）
```

|---|---|---|---|---|
| 0 | **FULL_MANAGER** | | 5 | EUROPEAN_TRADERS |

## 2. 对象定位法（全动态，跨会话免疫）

所有地址**不硬编码**——每次运行现场定位，避免进程重开 / 读档导致的地址漂移。

### 2.1 faction 定位

**vtable 全区域扫描 + 中文名匹配**：扫可读区域找 `== image_base + 0x15fac30` 的 4 字节值（`numpy` 向量化），
对候选读 `+0x0b14 → UTF-16 中文名` 与 `--faction` 参数比对。

> 注意：判断「对象存在」的最小读取跨度是 `MIN_OBJ = 0xb18`（要覆盖到 `+0x0b14` 读满 4 字节）。
> 滑窗按 `0xb18` 而非 `0x800` 推进，否则会漏对象。

**历史锚定法（已确证，可作交叉验证）**：国库值差分——游戏内改钱（如 `3000 → 2150 → 4516`），
三次读数取交集即国库字段，再由国库记录 `[+0x04]` 回指 faction 对象。

### 2.2 obj_A 定位

`cnt / tbl` 签名扫描 + **条目 key 是 faction 校验**。

### 2.3 manager 条目定位

按 §1.2：条目 key 直接等于目标 faction 指针；找不到则回退 `key + 0x164`。

### 2.4 定位缓存

`--cache` 把定位结果写入**工具目录下的** `.watch_cache.json`（运行时生成、不入库），之后毫秒级执行
（适合 AI 过回合极快的场景）；地址失效（读档 / 重进）自动回退全扫，
`--recache` 强制重新定位。

## 3. 写入流程与安全纪律

```
1. 定位 faction（§2.1）           → 校验 vtable
2. 定位 obj_A + 表结构（§2.2）    → 校验 cnt / tbl 合理、条目 key 是本 faction
3. 读原值备份（+0x6a0、manager_id）
4. 写 +0x6a0 = 0
5. 写 manager_id = 0 (FULL_MANAGER)
6. 回读两项确认
```

**硬性纪律**（写入类工具的通用约束）：
- **写前结构验证失败 → 禁止写**（宁可报错退出，不可猜测偏移）；
- **写后必须回读**，不一致即报失败；
- 一次只改一个变量，便于归因。

## 4. 人类的本质：一整套互相校验的状态

> ⚠️ **核心判据**：`+0x6a0` 只是这套状态露在外面的一个字段，**不是唯一开关**。

「人类派系」由以下若干处**互相校验**共同定义：

| 组成 | 位置 |
|---|---|
| human 标志 | `faction + 0x6a0` |
| local player 注册表 | `registry["LocalFaction"] @ [session + 0x1498]` |
| manager 表条目 | §1.2 |
| 回合 / UI / 任务 / 胜利条件 | 与 human 标志绑定的整套状态 |

**推论**：把 AI 派系「伪造」成人类（只翻 `+0x6a0`）必然与 local player 冲突而崩溃；
反之，「人类 → AI」方向（看海）之所以安全，是因为它是在**拆掉**玩家这套状态，
不产生第二个 local player。这也解释了为什么「恢复人控」必须**成对写回**。

**存档层对照**（`esfpy`，ESF 明文树，**已确证**）：`FACTION` 节点 `index 2` = 派系名、
`index 7` = `is_human`（↔ `+0x6a0`）；人类独有 `SHROUD` / 任务 / 胜利条件 /
`INGAME_MODIFIABLES(-2,-2,-2,1)` 等节点。

## 6. 已关闭路线（勿再投入）

以下路线均已**实机证伪**，重做只会重复付出成本：

| 路线 | 结果 |
|---|---|
| **manager 表单独直写 FULL_MANAGER** | ❌ manager 表**不是**人类控制开关——单写无效 |
| **AI 势力直接写 `+0x6a0 = 1`**（伪造人类标签） | ❌ 崩（local player 冲突） |
| **AI 派系改人类 `+0x6a0=1` + `manager=HUMAN`** | ❌ 崩——§4 所述，伪造状态不可能合法 |
| **`grant_faction_handover` 做单机看海** | ❌ handler `FUN_1060c510 → FUN_1059ab20` 写 `+0x7a8=1/+0x708=0`；参数**不是**移交目标，本地必被移交 → 无人类退出 |
| **存档改人类标签** | ❌ 同上，伪造状态不合法 |
| **清 `mgr+0xd18` / 写 `ws+8`/`+0xb` 隐藏天气 UI / 方案 A/B 等** | ❌ 属目标1/3 范畴的旧路线，均已证伪 |

另有一条**边界结论**（勿误用）：「无人类」退出检查**不读** `+0x6a0`——
所以不能靠它来判断看海是否生效，要以实际回合推进为准。

## 7. 已知限制

- **mod 兼容性未验证**：大改派系表 / 新增派系的 mod 可能改变对象布局或表规模，未做实测。
- **看海期间的 AI 内战**：若不叠加目标3（`[pending+0xb9]`），AI 之间的战斗走引擎**自动结算**，看不到战场。
  要观看需用目标3 工具（见 `40_GOAL3_MECHANISM_MAP.md`）。
- **恢复人控后的 UI / 任务 / 胜利条件同步**：反向写回已知**合法且可存档**，
  但长时间看海后切回人控时，界面与任务状态是否存在不同步**未系统验证**。
- 工具为**研究原型**，仅限单机；A1 类 hook 与内存写入均需管理员权限。
