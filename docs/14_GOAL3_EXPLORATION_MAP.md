## 2. 路线层（两条大路，逻辑互斥）

> 路线的区分建立在「引擎如何决定加载一场战斗」的**逻辑**上，不依赖具体地址；换地址不换路线。

### 路线1：AI 自身姿态触发加载（外部注入驱动加载机器）
- **逻辑依据**：引擎有台「战斗加载机器」（battle_mgr 创建链），入口条件 = 某参战方被识别为「人类」。AI 内战默认无人类参战方 → 机器不启动 → 自动结算。路线1 = 注入人为满足入口条件（哪怕足迹不完整），**强行把机器驱动起来**。
- **目标**：battle_mgr 创建 + 进场景。允许伴随卡死/崩（= 注入不完整的症状，逐个补）。
- **手段家族**：注入人类信息 / 其他注入引导 / 加载后拉双方 / 直接触发或完整伪造（见 §3）。

### 路线2：仿照人类存在（完整伪造「有人类参战」的数据足迹）——✅ 已闭环（2026-08-19）
- **逻辑依据**：引擎原生支持「人类与AI战斗」→ 战斗照常加载。证明引擎判「是否加载」的依据 = 「存在被识别为人类的参战方」**数据足迹**，不是操作者身份。路线2 = 完整复现足迹，让 AI 内战在引擎看来与有人类参战完全等同。
- **目标**：✅ **达成**。伪造支点定案 = **分叉输入 [pending+0xb9]=1**（1 字节）——让引擎走人类加载链，但本地玩家不参战 → setup 0x5cf168 天然旁观。
- **手段家族**（历史参考）：伪造参战方 / 伪造援军 / 伪造观察者——均被 b9 单字节方案取代为达成路径，保留作理解用。

- **行动（★P6 修正版，re_f8 Q2/Q5）**：复现状态 4 的静态自洽手段 = ①写 `[pending+0xb9]=1`（ready=0 时 FUN_105caa60 返回 0 → 状态 4，+0xb9 无其他写者覆盖）②**FUN_10600c20 在 pending 构造前生效**（登记链 → ready=1 + 条目+0xd=0 → 分叉自然返回 0）。⚠️ 原案「写 +0x54=0」被 0x6045c9 每 tick 重算覆盖，**不可持续**；0x6084db 注入时点太晚（pending 已构造、登记已失败）→ 仍走状态 6。前置 = K4 人类战斗观测（确认状态 4 真实存在 + 抓 FUN_105caa60 输入基线）。
- **判据**：AI pending 走到状态 4（首次实机观测到状态 4 在 AI 内战出现）+ battle_mgr 创建（⚠️ 状态 4 只解决 pending 分叉，加载仍需 battle env——P6 是路线2 必要非充分条件，F6 已证战役层无 env）。

### 4.2 技术路径 2-B：伪造援军（人类援军足迹）【⬜ 新，用户洞察支撑】

- **原理**：引擎原生「AI 战 + 人类援军加入」→ 战斗照常加载。援军的人类足迹比「完整参战方」可能更薄（只需「人类援军加入」语义）——**伪造援军足迹让 AI 内战带上一个"人类援军"**。
- **证据**：🔶 用户领域知识（AI vs AI + 人类援军可自主选择加入 = 引擎原生「人类存在但操作者是 AI」的加载实例）+ 机制自洽（Goal_3_LogBook 08-16）。
- **行动**：**纯观测零注入**：用户摆 AI 双方军队 + 人类援军 → 接受加入提示 → 捕获完整「人类援军存在」足迹（pending 字段 / env 装配 / 参战方表）→ 作为 2-A/2-D 模板。
- **判据**：捕获到「AI 战 + 人类援军」的完整数据足迹；对照 AI 内战差异点。

### 4.3 技术路径 2-C：伪造观察者（IsSpectator 足迹）【⬜ 未定】

- **原理**：如果引擎支持「观察者」身份参与战斗（env+0x281e8 IsSpectator），伪造观察者足迹可能触发加载（或至少在加载后能观看）。
- **证据**：🔶 **疑似需要先战斗加载**（用户：不好说）——IsSpectator=env+0x281e8（观察者标志，03 十五节确证）；若无战斗可加，观察者足迹可能不足以驱动加载本身。
- **行动**：①先确认「观察者足迹能否独立触发加载」（在 2-B 观测中顺带记录 IsSpectator 字段时序）；②若必须先加载 → 观察者足迹无法独立触发加载 → 2-C 关闭，主攻转 2-A/2-B。
- **判据**：观察者足迹能否在无参战战斗时触发加载（能 = 独立路线；不能 = 关闭）。

## 7. 边界总览（墙，不可逾越）

1. **battle_mgr 创建链只在 faction+0x6a0=1（人类分支）可达**——路线1 注入点 + 路线2 伪造目标；直建路径（0x608551）AI 场景结构性不可达（core 链断 + vcall=事件派发器 no-op），必须走 pending 状态机 → 状态 10 双门。
2. **battle_mgr 真实创建 = env 接口链**（FUN_101ebfa0 → wrapper 0x104e950 → FUN_110d22f0，读 env+0x281e8/0x281e4）；FUN_101ebfa0 静态死链 → 需 env 本体 + 装配（K1/K2）。
3. **双转人类证伪关闭（re_f8）**：状态 10 双门非加载门（AI 开战链尾部检查，与 battle_mgr 无静态调用边）；双人类足迹未登记 → 数据不一致崩（40s 崩根因修正）。**主攻 = 路线2 P6（复现状态 4）**，不是补双人类路径。
4. **battle_mgr 判据必须 + 触发源归因**（43 三次假阳性教训）——`verify_battle_mgr.py` 只验 vtable 不区分触发源，**须用户确认画面**。
5. **卡死 ≠ 崩溃**：进程活着 = 免费数据源 → 第一动作外部只读诊断（unstick --peek）；观察窗口要够长（type6 处理可能数分钟）。
6. **禁止**：伪造完成（UAF 崩）、伪对象注入（UAF 崩）、F hook（静默退出）、远程线程执行引擎代码（静默退出）、CCQ 直调 handler（非干净入口）。
7. **resume 被调 ≠ 完成**（条件性完成 API）；「完成标记 0x6 未出现」≠ 未完成（掩码保留 bit2）。
8. **type6 完成三路全封死**（1-H 闭环）——除非 1-A-3 证明必须，不再投入。
9. **观测期间用户操作会污染数据**；**观测前必须与用户确认游戏状态（正常 vs 卡死）**（L4 误判教训）。
10. **stub 生成后必须离线反汇编验证**（判定逻辑/重放完整性/指令边界/rel32/NULL 保护）。
11. **回放路线边界（P48）**：不解决「让 AI 内战加载」本身，只解决「已加载战斗的观看/复用/存档」。
12. **★路线归属纪律**：每次对话开头声明路线1 还是路线2；注入/驱动机器 = 路线1，观测/复现/伪造足迹 = 路线2；禁止把路线1 手段当路线2 目标追。
